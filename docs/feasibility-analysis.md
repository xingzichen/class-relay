# 微信群家委会智能维护系统可行性分析

## 1. 结论摘要

本项目的业务功能总体可实现，适合由具备浏览器插件、后端和知识库开发能力的个人开发者推进。

核心结论如下：

- **知识采集、图片理解、通知版本、混合检索、任务管理、Agent直接决策和自动发送在技术上可落地。**
- **最大不确定性是微信网页版，而不是Agent或本地模型。**
- **无法保证全年7×24小时完全无人干预。** 微信可能要求重新扫码、安全验证或限制网页版登录。
- **独立测试账号降低了主账号损失，但不消除平台规则风险。**
- **Qwen3.8-27B 6-bit适合中文、视觉和Agent工具调用，但量化版本必须单独验证多模态和结构化输出。**
- **群晖NAS适合承载数据库、附件、Agent服务和备份；主模型更适合运行在具有足够GPU或统一内存的主机。**
- **DeepSeek Harness适合作为可替换的Agent Runtime，不能代替业务内核、知识库和浏览器适配器。**

项目建议进入技术验证阶段，但在网页版登录、消息完整性和发送幂等验证通过前，不应承诺生产级无人值守。

## 2. 范围与假设

本分析基于以下前提：

- 使用独立微信测试账号；
- 使用微信网页版而非客户端Hook或私有协议；
- 浏览器插件由项目自行开发；
- 学校家长群默认只读，家委会群允许自动回复；
- DeepSeek Harness调用本地Qwen模型；
- Qwen3.8-27B采用6-bit量化并保留视觉能力；
- PostgreSQL、PGroonga、pgvector和附件服务部署在群晖Docker；
- Agent拥有是否发送的语义决定权；
- 宿主保留机械权限边界和可靠性控制。

## 4. Agent框架可行性

### 4.1 DeepSeek Harness的适配性

DeepSeek Harness是模型无关的Agent Harness。模型、工具、Session、存储和Agent Loop均可由插件组合，适合本项目自定义以下能力：

- 微信消息事件适配；
- 知识检索工具；
- 任务和Case工具；
- 发送动作工具；
- 事件审计；
- 发送权限Invariant；
- Agent运行回放。

它的优势是Typed Event、追加式Session事件和插件边界，适合开发者构建领域系统。主要风险是当前仍处于developer preview，接口可能快速变化。

应对措施：

- 固定Git tag或commit；
- 不在业务代码中直接依赖Harness内部类型；
- 定义项目自己的 `ReasoningEngine` 和Tool DTO；
- 保留直接调用Qwen的备用适配器；
- 升级前执行历史事件回放测试。

### 4.2 为什么不选择Hermes作为主干

Hermes提供较完整的个人Agent、Skills、浏览器和定时任务能力，但本项目仍需自行开发：

- 微信DOM适配；
- 消息幂等；
- 老师身份；
- 通知版本；
- 班级知识库；
- Outbox；
- 群权限和发送审计。

项目开发者能够承担这些工作，因此Hermes的开箱优势有限，而其通用工具面可能扩大生产权限范围。Hermes仍可用于早期Prompt和Skill试验，但不建议成为正式业务内核。

### 4.3 是否需要Agent Harness

严格来说，通知提取和问答可以通过直接调用模型完成。采用DeepSeek Harness的收益在于：

- 统一工具调用；
- 保留Agent事件轨迹；
- 组合Skills与插件；
- 支持多步骤检索和版本判断；
- 后续增加任务、Case和周期工作时无需重写Agent Loop。

因此本项目使用Harness是合理的，但必须保持可替换性。

## 5. 本地模型可行性

### 5.1 模型能力

Qwen3.8-27B为原生视觉语言模型，支持图片、视频、长上下文和Agent任务。其能力覆盖：

- 中文群聊理解；
- 图片通知识别；
- 文档结构化提取；
- 通知版本比较；
- 问题分类；
- 工具调用；
- 简短群回复生成。

### 5.2 6-bit资源估算

27B参数的6-bit权重理论数据量约20GB，实际运行还需要：

- 视觉编码器；
- KV Cache；
- 推理框架；
- 图片预处理缓存；
- 操作系统和并发余量。

建议：

| 可用GPU/统一内存 | 评估 |
|---:|---|
| 24GB | 可验证，需限制上下文和图片；余量较小 |
| 32GB | 推荐的最低舒适配置 |
| 48GB及以上 | 更适合并行运行主模型、Embedding和Reranker |

主模型不需要使用原生最大上下文。知识库承担检索后，32K或64K上下文足够。

### 5.3 量化风险

第三方6-bit量化可能出现：

- 未包含或不兼容视觉编码器；
- 工具调用格式错误；
- JSON Schema输出不稳定；
- 长图片或中文小字识别下降；
- 推理框架不支持模型全部特性。

上线前必须使用目标量化文件和目标运行时完成：

- 100张真实或脱敏通知截图测试；
- 结构化JSON提取测试；
- Tool Call一致性测试；
- 多轮检索工具测试；
- 低清晰度、长图和表格边界测试。

## 6. 知识库可行性

### 6.1 选型结论

推荐使用：

- PostgreSQL：事实、版本、任务、审计和Outbox；
- PGroonga：中文全文检索；
- pgvector：语义向量与HNSW；
- NAS文件目录：内容寻址附件；
- Qwen3-Embedding：向量生成；
- Qwen3-Reranker：候选重排。

单PostgreSQL方案能减少OpenSearch/Qdrant的同步与运维成本，同时保留未来拆分接口。对于单班级到多班级、百万级检索单元的增长目标具有足够空间。

### 6.2 群晖适配风险

部署前需确认：

- CPU架构为x86_64还是arm64；
- DSM和Container Manager版本；
- 可用内存；
- Docker镜像是否提供目标架构；
- 数据目录是否使用支持快照的卷；
- UPS和异常关机保护；
- 是否有异地或离线备份位置。

PGroonga官方提供基于PostgreSQL的Docker镜像；pgvector需安装到同一自定义镜像。应固定PostgreSQL主版本和扩展版本，不使用浮动 `latest`。

## 7. 微信接入可行性

### 7.1 可实现路径

浏览器插件可通过以下方式工作：

- Content Script观察消息DOM；
- 识别白名单群；
- 检测未读并导航到目标群；
- 读取文字、图片和文件链接；
- 将消息提交到本地API；
- 轮询或订阅Outbox；
- 将文本填入输入框并发送；
- 检查页面中是否出现发送结果。

### 7.2 核心未知项

必须通过实际账号验证：

1. 测试账号能否稳定登录网页版；
2. 白名单群是否完整显示；
3. 非当前群消息是否能通过未读导航可靠加载；
4. DOM是否提供稳定的消息或发送者标识；
5. 图片和文件是否允许插件本地保存；
6. 浏览器休眠或页面后台化时是否持续同步；
7. 网页更新后选择器失效的检测方式。

### 7.3 无法承诺的能力

- 登录过期后自动绕过扫码；
- 账号安全验证自动通过；
- 网页未同步的历史消息自动补齐；
- 微信升级后插件无需维护；
- 平台永不限制测试账号。

## 8. Agent直接发送的可行性

Agent直接决定发送在技术上完全可行。推荐做法是让Agent直接调用最终动作工具，而不是输出一段需要宿主解释的自然语言。

语义决定由Agent负责：

- 是否需要回复；
- 回复什么；
- 是否等待；
- 是否创建任务；
- 是否转入私下沟通。

宿主只负责：

- 目标群是否在白名单；
- 参数是否符合Schema；
- 来源ID是否存在；
- 同一决定是否已经执行；
- 是否超过限速；
- 系统是否处于暂停状态。

主要风险：

- 家长消息中的Prompt Injection；
- Agent引用错误版本；
- 对普通聊天过度回应；
- 对社交语境理解错误；
- 量化模型工具调用偶发失败。

降低风险的方法不是增加第二个Agent审批，而是：

- 缩小工具权限；
- 把群消息包装成不可信数据；
- 检索工具只返回当前有效知识；
- `SEND`要求提供存在的来源ID；
- 使用历史消息做回放评测；
- 先影子运行，再逐步扩大触发范围。

## 9. 合规与社会可行性

### 9.1 平台规则

浏览器插件自动读取和控制个人微信仍可能被视为未经授权的自动化。独立测试账号降低影响范围，但不消除风险。项目不得加入反检测、绕过验证或私有协议能力。

### 9.2 家委会边界

系统应坚持：

- 家委会在学校指导下履行沟通、支持和监督职责；
- 严格管理家长通讯群组的信息发布；
- 不以家委会名义违规收费；
- 不代表学校作决定；
- 不将个别意见自动描述为全体意见。

### 9.3 未成年人信息

项目可能处理未成年人信息。应做到：

- 明确目的和范围；
- 取得必要的老师、群管理员和家长知情；
- 默认本地处理；
- 最小化收集；
- 提供纠正和删除途径；
- 敏感Case短期保留；
- 禁止学生画像、排名和行为评分。

## 10. 运行与维护可行性

### 10.1 预期维护工作

长期维护主要包括：

- 微信页面选择器更新；
- 重新扫码；
- 模型和Harness升级验证；
- 知识纠错；
- 数据库备份演练；
- 学期切换与数据保留；
- 新增老师和群成员身份绑定。

### 10.2 单人维护可行性

采用单PostgreSQL、NAS文件存储和少量服务时，单人维护可行。若首版同时引入OpenSearch、Qdrant、Redis、MinIO和消息中间件，会显著增加备份、一致性和升级负担，不建议。

## 11. 粗略开发工作量

以下为一名熟悉TypeScript/Python、浏览器插件和Docker的开发者的全职等效估算，不含微信页面重大阻碍：

| 模块 | 估算 |
|---|---:|
| 微信插件PoC与消息采集 | 1.5～3周 |
| 数据模型、知识API和附件 | 2～3周 |
| 全文、向量和重排检索 | 1～2周 |
| DeepSeek Harness插件和Skills | 2～3周 |
| Outbox、发送与可靠性 | 1～2周 |
| 管理后台 | 1.5～3周 |
| 测试集、回放和影子运行 | 2～4周 |

可用MVP约需6～10个全职开发周；个人业余开发通常需要2～4个月。实际工期最受微信网页可用性和模型量化兼容性影响。

## 12. 风险排序

| 优先级 | 风险 | 影响 | 缓解措施 |
|---|---|---|---|
| P0 | 测试账号无法使用网页版 | 项目接入路径失败 | 最先做登录PoC |
| P0 | 非当前群漏消息 | 知识不完整、错误回答 | 未读导航、健康检查、人工对账 |
| P0 | 发送幂等失败 | 群内重复回复 | Outbox、decision_id、发送回执 |
| P0 | Prompt Injection导致误发 | 隐私与信任损失 | 不可信数据包装、最小工具权限、回放测试 |
| P1 | 老师身份不稳定 | 错把家长消息当事实 | 人工绑定、名称历史、冲突暂停 |
| P1 | 通知版本判断错误 | 引用过期信息 | 时间模型、证据、管理纠正 |
| P1 | 6-bit视觉或Tool Call退化 | 提取和发送失败 | 固定量化、专项评测、备用适配器 |
| P1 | Harness接口变更 | 升级成本 | 固定版本、隔离接口 |
| P2 | NAS性能不足 | 检索或任务延迟 | 调优、模型外置、未来拆分索引 |

## 13. Go/No-Go门槛

### Go条件

- 测试账号能连续登录并同步目标群；
- 插件能稳定识别群和自发消息；
- 7天采集测试没有不可解释的长期漏采；
- 目标6-bit模型完成图片和Tool Call测试；
- 通知版本回放集达到可接受准确度；
- Outbox重启测试不存在重复发送；
- 学校或群管理员接受测试范围和隐私说明。

### No-Go或调整条件

- 账号完全无法使用网页版；
- 网页只提供当前会话且无法可靠发现目标群未读；
- 无法区分测试账号自发消息，导致循环风险；
- 目标量化版本无法稳定视觉输入或工具调用；
- 群成员无法接受自动采集和回复；
- 需要绕过微信安全机制才能维持运行。

## 14. 推荐实施决定

项目可继续，推荐技术路线不变：

1. 先做微信网页版和目标6-bit模型双PoC；
2. 业务内核和知识库独立于Agent Harness；
3. 使用DeepSeek Harness承载Agent工具调用与事件轨迹；
4. 使用PostgreSQL + PGroonga + pgvector构建长期知识平台；
5. Agent直接决定发送，宿主保留最小机械保护；
6. 通过影子运行和历史回放后再开启真实发送。
